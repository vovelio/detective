# Этап 5 — долговечная общая доска

Доска использует существующие cookie, членство, CSRF и `POST /api/v1/rooms/{code}/actions`.
Игровые правила и `game_engine.apply` не изменены. Мутации доски равноправно доступны
всем участникам в INTRO, PLAYING, DISCUSSION независимо от очереди и роли ведущего.
В финальных фазах доска доступна для чтения. Это выбранная техническая политика этапа 5.

## Команды

Обёртка прежняя: `client_action_id` UUID, `expected_revision`, `type: "board_mutation"`,
`payload`. Payload имеет `op` и только перечисленные поля:

| op | Поля |
| --- | --- |
| card_transform | card_id, x, y, rotation, expected_version |
| stroke_create | object_id UUID, points: [{x,y}, ...] |
| arrow_create | object_id UUID, from: {x,y}, to: {x,y} |
| arrow_update | object_id UUID, expected_version, from: {x,y}, to: {x,y} |
| note_create | object_id UUID, x, y, text |
| note_update | object_id UUID, expected_version, x, y, text |
| object_delete | object_id UUID, expected_version |

**Уточнение пользователя этапа 5 выше UI_SPEC_FINAL:** стрелки свободные, протягиваются
между произвольными координатами; привязки к карточкам и card IDs в arrow payload нет.

Координаты конечные, ±1 000 000; поворот конечный и нормализуется к [0,360).
Штрих содержит 2–256 точек. Текст заметки — обычный текст 1–1000 символов, без HTML
интерпретации; управляющие ASCII-символы, кроме перевода строки/табуляции, запрещены.
Цвет/ширина штрихов фиксированы клиентом и не принимаются от сервера как произвольные поля.
Размер карточек фиксирован клиентом. Удаление карточки, resize и группировка отсутствуют.

Технические пределы на партию: 512 активных сохранённых объектов, 1024 сохранённых
идентификатора включая tombstones, 65536 активных точек штрихов. Исходные виртуальные
card_position version0 не занимают строки до первого перемещения. Эти пределы ограничивают
рост БД/ответа и являются инженерным выбором, а не новым игровым правилом.

## Snapshot

Персональный `/snapshot` дополнен `board: {objects: [...]}`. Каждый объект:

```json
{"id":"card:start-card","kind":"card_position","version":0,"payload":{"card_id":"start-card","x":0,"y":0,"rotation":0}}
```

- Для **каждой опубликованной карты**, включая стартовую, есть `card_position`,
  ID `card:<card_id>`, версия 0 до первого изменения. Payload содержит только
  card_id/x/y/rotation. `published[].position` также отражает сохранённое положение.
- stroke: payload `{points:[{x,y}]}`.
- arrow: payload `{from:{x,y},to:{x,y}}`.
- note: payload `{x,y,text}`.
- Созданные объекты имеют version1; обновление/удаление увеличивает её на 1.
- Удалённые объекты не выдаются. Tombstone запрещает повторное создание с тем же UUID.

Проекция allowlist; ORM и сырой серверный JSON клиентам не выдаются. Трансформация
принимает только card_id из `state.published`; рука, колода, сброс и чужая комната не
дают прав. Все скрытые/несуществующие card IDs дают один `BOARD_TARGET_INVALID`,
без повторения присланных данных в ошибке. Ресурсы карт остаются под существующим
контролем персональных views. Призрак приватной карты не является объектом доски.

## Транзакции и конфликты

Одна `games.revision` для игры и доски. room/game блокируются в прежнем порядке.
Объект, revision состояния, GameAction receipt и GameEvent сохраняются одним COMMIT.
На board-команду используется прежний fingerprint/UUID и сохранённая квитанция;
повтор после потерянного ответа проверяется до ревизии и ничего не применяет повторно.
Ошибки откатывают все изменения. Сессии/раздача/очередь не меняются.

По отдельному уточнению пользователя независимые изменения не конфликтуют по старой
общей ревизии: board принимает `expected_revision <= current`, но не future revision.
Игровые команды по-прежнему требуют точного совпадения. Изменение существующего объекта
требует точной `expected_version` (card_position начинается с 0). Поэтому независимые
параллельные изменения фиксируются оба; у одного объекта один winner, второй получает
`BOARD_VERSION_CONFLICT`, обновляет snapshot и предлагает повторное действие без скрытого
перетирания. Явный повтор неизвестного ответа сохраняет исходное намерение/UUID.

Остальные коды: BOARD_PHASE_INVALID, BOARD_LIMIT, BOARD_TARGET_INVALID, прежние
REVISION_CONFLICT/ACTION_ID_REUSED. Все ошибки безопасны и не содержат содержимого карты.

`board_objects` — отдельная таблица с составным PK game_id/id, типом, JSONB payload,
версией, deleted_at. Migration `9ab31d5e42c0` следует за `15d25b13ab98`; downgrade
убирает только таблицу доски. Сессионные таблицы и формат детективного сценария неизменны.

## WebSocket

Долговечные изменения используют прежний безопасный `state_changed` с revision/phase.
Клиент перечитывает snapshot; новый журнал или второй revision не нужен.
Курсоры как прежде эфемерны и содержат только координаты и серверный member_id.

Для движения **уже публичной** карты добавлено эфемерное сообщение:

```json
{"protocol_version":1,"type":"card_preview","card_id":"start-card","x":50,"y":80,"rotation":15,"version":0}
```

Сервер проверяет текущую сессию/членство/фазу, публичность карты и её сохранённую версию
по БД. Только затем пересылает другим сокетам комнаты тот же allowlist плюс серверный
member_id. Неизвестные поля, actor_id, тексты, hand IDs запрещены. Отказ на скрытую карту
не пересылает её ID другим. Preview не меняет БД/revision/ход и не раскрывает личный ghost.
Отдельный лимит 8 preview/сек на соединение в существующем общем 20 сообщений/сек;
лишние preview отбрасываются, bounded writer/timeout остаются прежними.

Клиент ограничивает отправку до 8/сек, хранит preview отдельно от snapshot, убирает
по TTL около 2с, reconnect/offline и при увеличении сохранённой версии. Финальный
`card_transform` идёт REST-командой с прежней версией и подтверждается обычным snapshot.
Камера остаётся локальной, не сохраняется на сервер и не рассылается.

В инструменте выбора заметка перемещается протягиванием и редактируется по клику.
Стрелка перемещается за линию; круговые ручки на концах меняют начало/конец отдельно.
Ластик принимает попадание в расширенную область линии и обоих концов.
Обновление стрелки проверяет тип объекта, версию, фазу и членство как note_update.
