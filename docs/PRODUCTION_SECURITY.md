# Production: конфигурация, ограничения и хранение

## Конфигурация, которая отказывается запускаться небезопасно

`APP_ENV=production` требует:

- `SESSION_COOKIE_SECURE=true`, только точные HTTPS `ALLOWED_ORIGINS` без wildcard,
  credentials, путей, query или некорректного порта;
- абсолютный `CASE_STORAGE_PATH` вне `/tmp`, `/var/tmp`, `/dev/shm`; фактический
  persistent mount обеспечивает Compose (`/data/cases`), а не один лишь абсолютный путь;
- явно заданные точные IP в `FORWARDED_ALLOW_IPS`, без `*`, подсетей/unspecified адресов;
- включённые HTTP rate limits; `HTTP_RATE_LIMIT_ENABLED=false` в production запрещён.

Dev-режим по умолчанию остаётся `development`: локальная loopback-cookie и прежние
запуски разрешены; HTTP limiter по умолчанию выключен. Для отдельной локальной проверки
его можно включить `HTTP_RATE_LIMIT_ENABLED=true`. Режим среды не меняет игровые правила.

Секреты читаются из `DATABASE_URL_FILE` и `TOKEN_HASH_PEPPER_FILE` либо из прежних
`DATABASE_URL`/`TOKEN_HASH_PEPPER`. Одновременное значение и `_FILE` для одного секрета
запрещены. Файл — regular file без следования симлинку, до16KiB UTF-8, одна непустая
строка с допустимым завершающим newline. Значения не отражаются в ошибках/repr.
Alembic использует тот же DATABASE_URL_FILE reader и не требует origin/pepper окружение
для отдельной миграционной команды. Pepper как ранее не короче32байт; генератор окружения должен создавать случайный секрет.

У Compose secret source-файлов могут быть0444 для чтения непривилегированным UID10001,
но родительский каталог на хосте остаётся0700. Это не разрешение сделать секреты
общедоступными: нельзя помещать их в Git, build context, публичную папку или логи.
Сохраняйте тот же pepper при обновлении/restore: его смена уничтожит возможность
использовать прежние анонимные cookies, даже если игровые строки остались в БД.

## HTTPS, Host и доверие reverse proxy

Production runner — один процесс `python -m detective.api --host 0.0.0.0 --port 8000`.
`--workers`/несколько API-инстанций не используются. API не имеет опубликованного порта.
Единственный внешний вход — Caddy, выполняющий TLS и HTTP→HTTPS перенаправление.

Uvicorn доверяет proxy headers только явно заданному Caddy peer. В штатной Compose-сети
это `172.30.0.2`; доверие всей сети или `*` не требуется. Middleware не читает
произвольный клиентский X-Forwarded-For самостоятельно; HTTP budgets используют
нормализованный `scope.client`, который Uvicorn меняет только для доверенного peer.
Подделанный X-Forwarded-Proto от другого peer не делает HTTP безопасным.

Для production `/api/*` требуется ASGI scheme HTTPS. `/health/live` и `/health/ready`
доступны по внутреннему HTTP для container healthcheck с правильным публичным Host;
это точечное исключение не открывает API по HTTP. HTTP Host проверяется целиком,
включая порт и единственность заголовка. Origin проверяется по точному списку для POST.

Secure cookie называется `__Host-detective_session`, содержит HttpOnly, Secure,
SameSite=Lax, Path=/ и не содержит Domain. JavaScript не читает token. CSRF proof
привязан к сессии и обязателен на изменяющих запросах кроме защищённого bootstrap.
Текущий WS guard требует WSS, единственный Host/Origin, cookie/членство и detective.v1;
query tokens и игровые команды через WS запрещены. Caddy должен сохранять публичный
Host и передавать реальную схему соединения. Нельзя исправлять ошибку proxy отключением
Secure/Origin/CSRF или расширением trust до всех адресов.

## HTTP budgets и ограничения ресурсов

Один API-процесс хранит bounded token buckets; дополнительные сервисы/Redis не нужны.
Бюджеты считаются по IP доверенного ASGI peer, а не по изменяемому cookie/actor_id:

| Класс | Среднее пополнение | Burst |
| --- | --- | --- |
| Все `/api/*` | 2400/мин | 240 |
| POST sessions | 30/мин | 10 |
| Создание комнаты | 10/мин | 5 |
| Присоединение | 60/мин | 20 |
| Импорт | 12/час | 3 |

Это token bucket, а не календарное фиксированное окно. Route budget применяется вместе
с общим. При исчерпании — безопасный `RATE_LIMITED`, HTTP429 и Retry-After в секундах.
Ключи/IP/токены не логируются. Таблица максимум4096ключей, sweep раз в60с удаляет idle
ключи старше1часа. При заполнении новые ключи отклоняются, активные budgets не вытесняются
ради обхода лимита. После рестарта buckets обнуляются; это не обещание распределённой
или DDoS-защиты. Общий NAT/IP делит budget: пределы следует проверить на ожидаемой группе
и адаптировать осознанно, не отключать limiter в production.

Обычный JSON body ≤32KiB, чтение не дольше10с (`REQUEST_TIMEOUT`408). Импорт остаётся
отдельным точным multipart-маршрутом с прежними лимитами20MiB+64KiB/30с и validator child
CPU/wall/memory caps. Подробности — IMPORT_API.md. WS сохраняет свои bounded queues,
frame/rate/connection limits и heartbeat. Секретные изображения доступны только через
авторизованный endpoint; каталог cases не публикуется Caddy.

SQLAlchemy echo выключен, параметры скрыты; Uvicorn access log выключен, уровеньwarning.
Не включайте debug WS/SQL или вывод request body/cookies. Backup также содержит личные
руки и ключи — он должен быть приватным и недоступным из frontend/Caddy.

## Backup, согласованность и обновления

Обязательный набор восстановления: PostgreSQL, CASE_STORAGE_PATH, pepper, секреты БД,
версии приложения/миграции и public-конфигурация. Снимок следует делать при остановленной
записи/API: это согласует pg_dump с cases и устраняет гонку импорта/изменения партии.
Процедура и команды — DEPLOYMENT.md и инфраструктурные scripts. Хранить копию только
на том же VPS недостаточно; офлайн/внешняя копия — обязанность оператора перед выпуском.

Проверка восстановления должна выполняться в отдельном проекте/томах с тем же pepper,
не поверх живых данных. Downgrade импорта при существующих room-scoped сценариях
намеренно запрещён; нельзя обходить запрет удалением пользовательских данных.
Безопасный откат — проверенный полный backup/совместимая версия либо отдельный план
миграции данных. Обновление сначала проверяется на копии, затем после backup/остановки
трафика выполняется единственным migrator до запуска API.

## Предложение retention — ещё не утверждено

**Удаление не реализовано и не запускается автоматически.** До решения владельца все
комнаты/партии/импорты сохраняются. Предлагаемая политика для отдельного утверждения:

- не начатое лобби:30дней без активности;
- незавершённая партия:90дней без активности;
- завершённая FINISHED-партия:90дней после завершения;
- импортированные сценарии: пока существует комната или любая партия/другая запись,
  использующая пакет; файл удаляется только после проверки всех SHA256-ссылок;
- истёкшая анонимная сессия: grace30дней для административного анализа, без доступа по
  истёкшей cookie; связанные комнаты/партии нельзя каскадно удалять раньше своей политики;
- временные/orphan-файлы: не раньше7дней, только после подтверждённого отсутствия ссылок,
  согласованного backup и проверки, что нет активной публикации архива.

Текущая БД не содержит единого достоверного last_activity/finished_at для этой политики:
есть created_at/joined_at/GameAction.created_at, но не полная история просмотра/присутствия.
Перед любым будущим purge нужны отдельная миграция, правила touch/activity и dry-run
аудит. **Нельзя подменять неактивность возрастом created_at.** Очистка связанных rows
должна учитывать frozen game manifest, assets, членство, действия, события, доску и
комнатные сценарии, а также совместно используемые digest-файлы.

Срок cookie сейчас30дней от создания без продления. Хранение партии90дней не обещает
возвращение на прежнее место после expiry/потери cookie: идентичность не восстанавливается
автоматически. Изменение session lifetime/recovery UX — отдельное продуктовое решение.

## Проверки этого модуля

Автоматические тесты проверяют fail-closed environment/secret files, безопасные ошибки,
лимиты/refill/табличную ёмкость, production-cookie/CSRF/Host/HTTPS, slow JSON и сохранение
размера body, отказ от поддельного XFF, native Uvicorn trust/не-trust forwarded proto.
Проверка TLS/Caddy/Docker/backup-restore — отдельный интеграционный контур этапа7;
прямая HTTP-проверка Uvicorn не выдаётся за доказательство HTTPS.


## Проверка зависимостей при подготовке этапа7

Повторная проверка runtime-lock по OSV выявила известные advisory для прежних
Pillow11.2.1, Starlette0.46.2 и setuptools80.9.0. Для production зафиксированы
Pillow13.0.0, Starlette1.10.0, setuptools84.2.1. Совместимость Starlette обеспечена
FastAPI0.135.0; его обязательная небольшая зависимость annotated-doc0.0.6 добавлена
в оба lock-файла. Игровая механика/формат сценариев не менялись.

После обновления OSV querybatch для29 runtime-пакетов вернул пустой список findings.
Это точечная проверка известных Python-advisory на момент работы, а не гарантия
отсутствия всех уязвимостей в приложении/ОС/образах. Перед выпуском и далее регулярно
проверяйте зависимости/базовые образы и повторяйте регрессии после патчей.
Источники проверки: https://api.osv.dev/v1/querybatch и metadata официального PyPI.


Реальный двухигроковый Docker E2E выявил, что первоначальный общий бюджет600/мин
блокировал быструю совместную работу с одного NAT. Игровой refresh теперь получает
один персональный snapshot, а не три запроса (room/catalog неизменны после старта).
Общий бюджет2400/мин burst240 учитывает до8 игроков и poll interval250мс; отдельные
бюджеты sessions/create/join/import не увеличены. Автоматически проверены разрешённые
NAT-snapshots и отказ настоящему flood, лимитер в production не отключается.
