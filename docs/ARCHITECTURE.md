# ARCHITECTURE — технический проект MVP

## 1. Стек

- Frontend: React + TypeScript + Vite; состояние UI локально и снимки состояния от сервера.
- Backend: Python + FastAPI, один API-процесс для MVP, WebSocket для реального времени.
- Данные: PostgreSQL, SQLAlchemy (async), Alembic.
- Сеть: Caddy для TLS, статического фронтенда и reverse proxy `/api`, `/ws`.
- Инфраструктура: Docker Compose, VPS, файлы сценариев на серверном volume.
- Внешний голосовой чат. Без Redis, очередей и Kubernetes в MVP.

## 2. Границы модулей

```text
frontend / React
  ├─ rooms & lobby (REST)
  ├─ game (WS + snapshot REST)
  ├─ board (локальная камера + командные события)
  └─ case import (.detective)
              │ HTTPS / WSS
           Caddy
              │
FastAPI (один процесс)
  ├─ sessions (anonymous cookies)
  ├─ rooms / memberships / host
  ├─ scenarios (ZIP + JSON Schema validation + assets)
  ├─ game_engine (pure deterministic logic)
  ├─ game_service (commands, DB transactions, idempotency)
  ├─ board_service (objects, versions, ownership checks)
  ├─ realtime (snapshot, redacted events, connected clients)
  └─ results (manual review, scoring)
              │
       PostgreSQL + assets volume
```

`game_engine` не знает о HTTP, SQLAlchemy и браузере. Он принимает состояние, команду и возвращает новое состояние/доменные события либо отказ. Сервис проверяет авторизацию, проводит транзакцию, сохраняет версию и публикует безопасное событие.

## 3. Модели БД (логическая схема)

| Таблица | Главные поля | Ограничения |
| --- | --- | --- |
| `anonymous_sessions` | id, token_hash, created_at, expires_at | токен не хранить в открытом виде |
| `rooms` | id, code, host_member_id, selected_case_id, status, created_at | code уникален |
| `members` | id, room_id, session_id, nickname, joined_at, online_at, seat | одна сессия — один участник в комнате |
| `scenarios` | id, owner_session_id, slug, version, path, checksum, imported_at | авторский архив, приватный для комнаты |
| `games` | id, room_id, scenario_id, phase, revision, active_seat, deck_cursor, turn_order, intro_ack | состояние меняется по транзакциям |
| `game_cards` | game_id, card_id, zone, owner_member_id, position_in_deck, board_x, board_y | zone ∈ deck/hand/board/discard, уникальность card_id в партии |
| `board_objects` | id, game_id, kind, payload_json, version, deleted_at | тип: stroke, arrow, note, card_position |
| `team_answers` | game_id, question_id, selected_option_id, reviewed_correct | один ответ на вопрос на партию |
| `game_actions` | id, game_id, session_id, client_action_id, game_revision, command_type, result_json, created_at | уникальный (game_id, session_id, client_action_id) |
| `game_events` | id, game_id, revision, event_type, public_json, created_at | аудит и повторная синхронизация |

Точное SQL-представление можно нормализовать в миграциях без изменения внешних контрактов.

На этапе 2 физическое хранение: `games.state` — единый серверный JSONB-конверт ядра
(включая карты/очередь/ответы), с отдельными `phase`/`revision`; `game_cards` и
`team_answers` пока не выделены в таблицы. Нормализация не нужна для атомарности MVP.
Сценарии пока только встроенные, устанавливаются операторским CLI; архивы хранятся по
checksum-имени в CASE_STORAGE_PATH. Авторство импорта/board_objects — будущие этапы.
Фактические таблицы и команды описаны в `API.md`.

## 4. Анонимная сессия и восстановление

- На первом входе сервер выпускает криптографически случайный opaque token (не JWT) и устанавливает cookie `HttpOnly; Secure; SameSite=Lax; Path=/` (в HTTPS); в БД хранится **хеш** токена.
- Предлагаемый срок cookie: 30 дней; срок жизненного цикла комнаты и политика удаления архивов настраиваются сервером.
- Браузер автоматически отправляет cookie с REST/WS, сервер находит связанную комнату и существующее членство. Обновление/F5 **не создаёт второго игрока**.
- После сетевого восстановления клиент вызывает snapshot и подписывается на события по ревизии. Возвращаются никнейм, личная рука, текущий ход, фаза, стол и общий статус. При потере cookie идентичность не восстанавливается автоматически; пользователь получает понятное сообщение.
- `online` вычисляется по соединениям/heartbeat, а не как вечное состояние игры. Дисконнект не удаляет игрока или карты. Критически важные данные не хранятся только в оперативной памяти API.
- Если ведущий временно отключился, его роль сохраняется. Автоматическая и ручная передача роли сейчас не реализуются: команды и UI не согласованы. Возможность явной передачи можно добавить позднее отдельным решением.

## 5. Конкурентность, идемпотентность

- Команда изменения игры содержит `client_action_id` (UUID), `expected_revision` (целое) и payload.
- Команда исполняется в транзакции с блокировкой строки `games` (`SELECT … FOR UPDATE`), проверкой авторства, фазы, активного игрока и версии.
- В одной транзакции изменить карты, добор, ход, ревизию и `game_actions`. Повтор с тем же action ID возвращает уже сохранённый результат.
- При конфликте ревизий возвращать `conflict` и актуальную ревизию/snapshot. Не допускать двойной раздачи.
- После COMMIT отправлять `state_changed` подключённым участникам. Если клиент пропустил событие — повторное получение snapshot обязательно.

## 6. События и приватность

**Золотое правило:** сервер формирует отдельный `public_state` и `private_state_for(member_id)`. Нельзя отправлять полный внутренний ORM-объект с «маской» на фронтенде.

- Общий snapshot: фаза, игроки, онлайн-статусы, текущий ход, кол-во карт в колоде/руках (без содержания), опубликованные карты, положение объектов и разрешённые действия.
- Приватный snapshot владельца: собственная рука с полными блоками, уведомления об ошибках.
- До `RESULTS` запрещены чужие руки, содержимое сброса, `role`/`logic_notes`/`supports_questions` и `solution`. Порядок колоды не публикуется.
- В `LOBBY`, `INTRO`, `PLAYING`, `DISCUSSION`, `ANSWERING` ключ недоступен всем, включая ведущего. После фиксации ответов в `REVIEW` только ведущий получает `correct_option_id`, `explanation`, `evidence_card_ids`; остальным ключ недоступен. Ответы заблокированы.
- В `RESULTS` и `FINISHED` всем участникам доступны ключ, разгадка, карточки и итог. Переход `RESULTS → FINISHED` — явная команда ведущего; после неё игровые действия запрещены.
- WS имеет `hello`, `state_changed`, `board_changed`, `presence`, `cursor`, `error`, `sync_required`; схему версионировать (`protocol_version: 1`).
- Текущие движения мыши и курсоры — временные ограниченные по частоте сообщения; **не** источник состояния и **не** обязательная часть истории в БД.
- Стрелки, заметки, окончательные штрихи и позиции карточек — долговечные объекты, версии и сохранение.

## 7. API (контракт уровня MVP)

| Метод | Путь | Действие |
| --- | --- | --- |
| POST | `/api/v1/sessions` | начать/продолжить анонимную сессию; cookie |
| POST | `/api/v1/rooms` | создать комнату с никнеймом; автор становится ведущим |
| POST | `/api/v1/rooms/{code}/join` | войти в лобби / вернуть своё место |
| GET | `/api/v1/rooms/{code}` | лобби и права текущего участника |
| GET | `/api/v1/cases` | доступные встроенные дела |
| POST | `/api/v1/rooms/{code}/cases/import` | загрузить `.detective` с валидацией |
| POST | `/api/v1/rooms/{code}/cases/select` | выбор дела ведущим |
| POST | `/api/v1/rooms/{code}/start` | начать и раздать |
| GET | `/api/v1/rooms/{code}/snapshot` | снимок с приватными полями только текущего игрока |
| POST | `/api/v1/rooms/{code}/actions` | игровая команда (`play_card`, `advance_phase`, `answer`, `review_answer`, `board_mutation` и др.) |
| GET | `/api/v1/rooms/{code}/result` | итог после проверки |
| GET | `/api/v1/rooms/{code}/assets/{asset_id}` | ресурс только видимой этому участнику карты |
| WS | `/ws/v1/rooms/{code}` | события и presence/cursor |

Типовая команда:

```json
{"client_action_id":"e58bbed4-6858-4cbc-9934-ad12411b57f9","expected_revision":12,"type":"play_card","payload":{"card_id":"clue-07","mode":"reveal","x":250,"y":120}}
```

Ошибка:

```json
{"error":{"code":"NOT_YOUR_TURN","message":"Сейчас ход другого игрока"},"revision":12}
```

## 8. Защита импорта/публичного сервера

- Проверять `Content-Type` лишь как подсказку; валидировать magic bytes ZIP и `case.json` против схемы.
- Рабочие лимиты: ZIP до 20 MiB, распакованные данные до 80 MiB, не более 100 файлов, ограничение глубины путей. Запрет `../`, абсолютных путей, симлинков, вложенных архивов и исполняемого содержимого.
- Разрешённые медиа: PNG/JPEG/WebP; сервер проверяет фактический формат и размер. SVG/HTML/JS не разрешать.
- Не доверять Markdown/HTML внутри карт: хранить/отображать структурированный **обычный текст**, экранировать в React.
- Rate limiting для создания комнат и импорта, ограничение размеров сообщений WS и частоты курсоров.
- Проверять Origin у WebSocket и cookie-based POST, использовать CSRF-защиту для меняющих состояние REST-методов.
- Секреты в env, логи без cookie/текстов приватных карт; запросы на просмотр объектов проверяют членство в комнате.

## 9. Наблюдаемость и тестирование

Структурированные логи без секретов, health endpoints `/health/live` и `/health/ready`, метрики активных комнат/WS, автоматические миграции контролируемым шагом, интеграционные тесты на транзакции и перезапуск. При внешнем доступе обязательны HTTPS и backup БД+assets. См. `DEPLOYMENT.md`.

## Реализация этапа 2

REST этапа 2 дополнен WebSocket на этапе 3; `/cases/import` остаётся этапу 6.
Ответы игровых команд — сохранённые квитанции, без исторических приватных snapshot;
после успеха/ретрая клиент получает актуальный персональный `/snapshot`.
`start` также принимает `client_action_id` и `expected_revision` (до старта — 0).
Типы команд и CSRF-контракт уточнены в `API.md`. На bootstrap `/sessions` обязательны
Origin/JSON; на остальные POST также обязателен session-bound X-CSRF-Token.


## Реализация этапа 3 — синхронизация

`detective.realtime` — транспорт в том же процессе FastAPI, без Redis/новых сервисов.
Один poller на подключённую комнату читает `games.revision` и подтверждённые `game_events`
в REPEATABLE READ. Поэтому доставка происходит после COMMIT и восстанавливается по БД,
даже если уведомление из памяти потеряно. Hook до COMMIT и отдельный движок WS отсутствуют.
Схема БД не менялась: outbox этапа 2 уже сохраняется атомарно с состоянием.

На соединение выделены ограниченная очередь и единственный writer. В ней только
безопасные уведомления, presence и курсоры; персональные views читаются через REST.
Регистрация нового сокета сверяет его baseline с watermark общего poller; resume после
REST-snapshot обнаруживает изменения во время подписки. Исторические события не содержат
рук и не используются для повторного разыгрывания карт. Разрыв журнала требует snapshot.

Состав лобби сравнивается с подтверждёнными строками rooms/members, отдельная игровая
ревизия на join/выбор дела не вводится. Presence и курсоры временные, не записываются
в БД. После F5/обрыва/рестарта клиент подключается с прежней cookie и получает свежий
snapshot; роль ведущего и ход не меняются. Протокол/лимиты — WEBSOCKET.md.
Один процесс остаётся обязательным для единого presence; межпроцессной шины нет.


## Реализация этапа 4 — React-прототип

Frontend — React/TypeScript/Vite без отдельной библиотеки состояния/роутера.
SessionController хранит последний серверный snapshot и локальные состояния UI;
RoomSync объединяет fetch, отбрасывает ответы старого поколения и реализует
hello/resume/heartbeat/reconnect. Команды не применяются оптимистично.

ApiClient использует same-origin cookie/CSRF. Намерение команды сохраняется перед POST
в sessionStorage отдельно для комнаты; повторы используют исходный UUID и payload.
Ни токены, ни snapshots/тексты карт в localStorage не сохраняются. В localStorage
только boolean-настройка подтверждения публикации. В WS личные данные не отправляются.

Необходимое совместимое уточнение: REVIEW-ведущий видит private.reviewed_answers
из существующего состояния, чтобы пережить F5 при ручной проверке. Остальным это
поле недоступно. Миграции, игровые команды и правила не менялись.
Локальная топология: Vite 127.0.0.1:5173 → /api,/ws proxy с исходным Host/Origin →
Uvicorn 127.0.0.1:8000 → PostgreSQL. Caddy/Docker/VPS остаются этапу 7.
Структура клиента — FRONTEND.md, запуск — LOCAL_UI.md.


## Реализация этапа 5 — общая доска

Новая UI-спецификация UI_SPEC_FINAL.md имеет приоритет над UI_SPEC.md. Уточнение
владельца от16 ноября2026 разрешает свободные стрелки, временные движения публичных
карт и независимые изменения разных объектов. Остальные правила игры прежние.

`api.board` — отдельный сервис версий/allowlist-проекции/аннотаций; чистый game_engine
не знает о доске и HTTP. Отдельная таблица board_objects хранит окончательные позиции,
повороты, штрихи, свободные стрелки и заметки. Исходные позиции карт сохраняются в ядре,
текущие transforms накладываются в представлении. Таблица, GameState.revision, receipt
и безопасный outbox меняются атомарно под прежними room/game locks. Чтение snapshot
блокирует game для согласованной пары revision/objects.

Сохраняется одна общая revision; только board-команды допускают старую общую ревизию,
проверяя версию своего объекта. Это позволяет принять изменения разных объектов, не
позволяя молча перетереть один объект. Создания имеют UUID, удаления оставляют tombstone.
Все серверные изменения проверяют членство, фазу и видимость игровых карт.

React BoardGame хранит индивидуальную камеру и локальные жесты. WS cursor/card_preview —
временный отдельный слой; публичность/версию preview проверяет сервер. Private ghost
не покидает браузер владельца. Durable изменения приходят через state_changed → snapshot.
Новых сервисов/зависимостей не добавлено. Контракты — BOARD_API.md, клиент — FRONTEND.md.


## Реализация этапа 6 — защищённый импорт

Один отдельный multipart endpoint сохраняет прежние Origin/Host/cookie/CSRF/права;
общие JSON POST≤32KiB не ослаблены. import_service ограничивает поток/время и количество
одновременных загрузок, import_worker проверяет существующим валидатором в отдельном
короткоживущем процессе с CPU/memory/wall limits. Это локальный служебный процесс,
не микросервис и не исполнитель кода из пакета.

ScenarioRow.scope_room_id отделяет встроенные дела от комнатных. Авторский manifest.id
не меняется; непрозрачный room-scoped ID каталога проверяется при выборе/старте.
Room.catalog_revision участвует в poller fingerprint и вызывает прежний room_changed;
нового WS-типа не требуется. Клиент загружает безопасный комнатный каталог при refresh.

package_storage устанавливает digest-addressed архив приватно через временный файл,
fsync и атомарную установку без перезаписи. Метаданные записываются только после
долговечного файла, под блокировками PostgreSQL. Проверка и очистка при откате не
удаляет архив, на который есть подтверждённые ссылки. При неустановимом исходе COMMIT
сохраняются приватные непривязанные байты, а не рискуют доступностью подтверждённых дел.
Подробности границ двух хранилищ и технические лимиты — IMPORT_API.md.


## Production-инфраструктура этапа7

Compose использует Caddy со статическим frontend, один non-root API и PostgreSQL18
в private network. У API/БД нет опубликованных портов. Отдельные persistent volumes
для database/cases/Caddydata/config, явные cases-init и migrate, health/restart-policy.
Caddy имеет фиксированный адрес вне динамического IPAM range; только он доверен API.
Runtime БД — отдельная detective_app NOSUPERUSER; административный secret не передаётся
API. Файлы секретов и согласованный offline backup сохраняют возможность восстановления.
Автоматического удаления данных нет; retention остаётся предложением. Технические
команды — DOCKER_OPERATIONS.md, безопасность — PRODUCTION_SECURITY.md.
