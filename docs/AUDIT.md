### Сессии и приватность

Opaque token — 32 случайных байта; в БД HMAC-SHA256 с серверным pepper. Cookie HttpOnly,
Secure, SameSite=Lax, Path=/, без Domain; в HTTPS имя с префиксом __Host-. В локальном
HTTP Secure можно отключить только для loopback origins. Срок сессии фиксирован: 30 дней.
Действующий bootstrap возвращает CSRF proof и свои комнаты, не заменяет членство.
Истёкшая/поддельная cookie — 401; удалённая cookie не восстанавливает прежнюю личность.

POST требуют разрешённый Origin и application/json; кроме bootstrap также обязателен
session-bound CSRF proof. Проверяется Host, запрещён Sec-Fetch-Site: cross-site.
actor_id разрешается только из cookie → session → member, не из входного JSON.
Лишние поля отвергаются. Ошибки не отражают body/значения, SQL-параметры скрыты.
Лимит POST — 32 KiB, логи не содержат cookie/рук/ключей.

Используется views.private_state_for: чужие руки, колода/сброс и авторские пометки
закрыты; REVIEW выдаёт ключ только ведущему, RESULTS/FINISHED — разгадку всем участникам.
Изображения разрешены только по assets видимых карт: владелец теряет доступ после сброса.
Ответы no-store/private, nosniff; Cross-Origin-Resource-Policy: same-origin запрещает
использовать приватные ресурсы как встраиваемые изображения на другом origin.

### Атомарность и идемпотентность

Каждому запросу выделяется своя AsyncSession. Единый порядок SELECT FOR UPDATE:
rooms, затем games. Старт/вход/выбор сценария/игровые команды не гоняются между собой.
Запись состояния, ревизии, квитанции и безопасного события — один COMMIT.
Ошибка откатывает всё. Уникальные ограничения дополнительно защищают action ID,
членство/ник/seat; ведущий связан составным отложенным FK именно со своей комнатой.

Повтор (game_id, session_id, client_action_id) проверяется до expected_revision;
идентичный запрос возвращает сохранённую квитанцию, не выполняя команду ещё раз.
Изменённый запрос под прежним ID — ACTION_ID_REUSED; новый ID со старой ревизией —
REVISION_CONFLICT с текущей ревизией. Исторические snapshot в квитанциях не хранятся,
поэтому повтор не раскрывает уже сброшенную руку. Клиент получает актуальный /snapshot.
Ошибочные команды не резервируют ID; отменённая команда сохраняет квитанцию без
изменения ревизии и без события. Повтор старта не перемешивает карты.

### Протокол и порядок

Endpoint /ws/v1/rooms/{code}, subprotocol detective.v1, protocol_version=1.
Cookie проверяется существующим HMAC/session механизмом. Handshake требует точный
Origin/Host (с портом), членство, поддерживаемый subprotocol; query string запрещён.
В Secure-режиме требуется WSS. Посторонние/истёкшие сессии не получают доступ.
Игровые действия остаются REST+CSRF через прежний транзакционный сервис.

hello содержит только свой member_id, ревизию/фазу и snapshot_url. Клиент читает
персональный REST-snapshot и отправляет resume. При изменениях за время fetch/обрыва
получает sync_required и перечитывает snapshot. События не воспроизводят игровые ходы.
Ключ, руки и ресурсы доступны только через прежние безопасные views/REST-авторизацию;
в WS они не передаются вообще, включая ключ ведущему в REVIEW.

На подключённую комнату один poller: каждые 250 мс он в REPEATABLE READ читает
подтверждённые games.revision/game_events и публичный состав комнаты, не games.state.
При обычной непрерывной последовательности уведомления идут по возрастанию revision.
Полный public_json из БД не рассылается: сообщения формируются по allowlist revision/phase.
COMMIT виден poller независимо от callback или процесса, выполнившего сервисную команду.
Rollback и идемпотентный повтор не дают второго state_changed.

При event gap или backlog >128 отправляется sync_required вместо неполной истории.
resume сверяет ревизию и наличие сохранённых событий в PostgreSQL; после рестарта
новый hello и snapshot возвращают авторитетное состояние. Регистрация проверяет
baseline нового сокета относительно уже работающего room-poller; устаревшие клиентские
ревизии не пропускают изменения между snapshot и подтверждением. Восстановление не
зависит только от памяти: подтверждённые действия/ревизии/события остаются в БД.

room_changed отражает состав/дело лобби без новой игровой механики или фиктивной
игровой ревизии для join. Presence — временные online-статусы по активным сокетам;
закрытие одной из нескольких вкладок не делает игрока offline. Потеря ведущего не
меняет его роль, карты и очередь. Cursor — только серверный member_id и конечные
координаты, без текстов/ID карт, без записи в БД.

### Надёжность и ограничения ресурсов

На сокет — один writer и bounded queue: 64 сообщения, максимум 256 KiB; кадр до 8 KiB.
Вход — JSON до 4 KiB, 20 сообщений/с; cursor до 10/с, лишние координаты отбрасываются.
Соединений: 4 на участника, 32 на комнату, 256 на процесс. DB/send timeout по 5 с;
app ping каждые 15 с, timeout 45 с. Uvicorn runner ограничивает ingress 4096 байт,
очередь transport 8, compression off, отключает access log. Debug-логирование WS запрещено.

Медленные/перегруженные сокеты закрываются с 1013, heartbeat timeout — 4408,
истёкшая сессия — 4401. Из очередей не извлекается личная информация, которой там нет.
При разрыве отменяются и ожидаются все дочерние tasks, освобождаются очереди/ссылки;
после последнего сокета комнаты poller отменяется и room-stream удаляется.
Никаких автоматических ходов, передачи ведущего, таймеров игры, Redis или иных сервисов.

### Persistence, конкуренция и безопасность

board_objects хранит public card_position, stroke, arrow, note с версией/tombstone.
Для ещё не двигавшейся public карты проекция формирует version0 из ядра. Сохранённый
transform накладывается в board.objects и published.position. Персональные views
карт/ресурсов не ослаблены. Snapshot блокирует game для согласованных revision/objects.

Долговечная board_mutation использует прежний /actions, cookie/CSRF, room→game locks,
client_action_id, receipt и outbox в одной транзакции. Общая games.revision одна;
board-команда допускает прошлую общую revision, но existing target требует точной
expected_version. Независимые изменения фиксируются оба, same-target конфликт получает
409 и актуальный snapshot. Будущая общая revision запрещена; игровые команды по-прежнему
требуют точного совпадения. Текущая очередь, добор, фазовые условия не меняются.

Итог drag/rotate отправляется только на отпускание. Временный WS card_preview
принимается исключительно для public карты с проверкой сессии/членства/фазы/версии
по БД; сервер подставляет member_id, пересылает allowlist. Нет приватного текста,
role/logic_notes/ключа/содержимого колоды/сброса. Preview не пишет БД/историю и не
передаёт ход. Клиент preview≤8/сек, cursor≤4/сек (серверные пределы8/10, общий20).
Preview TTL2с, cursor15с; reconnect/offline/new canonical version убирают previews.

Лимиты: координаты ±1e6 finite, штрих2–256 точек, заметка1–1000 символов обычного
текста, 512 active objects/1024 total IDs/65536 active stroke points. Значения —
инженерные пределы, не новая игровая механика. Ошибки не отражают входные секреты.
Ластик/команды удаления не могут удалить игровую карту. Стрелки содержат только
координаты, поэтому не могут ссылаться на скрытую карту.

Клиент хранит исходную object version во время drag. Независимые remote revisions
не сбрасывают жест/черновик. При конфликте нет autooverwrite, показана причина;
черновик заметки сохраняется для копирования/повторного осознанного редактирования.
Неизвестный HTTP-ответ использует прежний механизм pending/повтора с тем же UUID,
в том числе после F5. В sessionStorage нет cookie/CSRF/snapshot/текстов карт/ключей;
pending заметки содержит только введённый пользователем текст публичной аннотации.

### Безопасность обработки и хранения

Существующий валидатор проверяет ZIP≤20MiB/распаковку≤80MiB/≤100 файлов, пути,
симлинки/дубли, JSON/версию/ссылки/ID, фактические PNG/JPEG/WebP≤16млн пикселей.
Архив не извлекается, код из него не выполняется. Имя/MIME клиента не являются
доказательством формата и не используются как файловый путь.

Дополнительные HTTP-лимиты: multipart≤20MiB+64KiB, одна часть file; bounded headers,
чтение тела≤30с, максимум2 одновременных импорта/процесс, максимум16 дел/комнату.
Проверка выполняется отдельным короткоживущим процессом: wall10с, CPU5с,
RLIMIT_AS512MiB там, где ОС поддерживает; выходной manifest≤8MiB. При timeout/отмене
child принудительно завершается и ожидается. Это не исполняющий пользовательский код
сервис и не новый формат. Ограничение30+10с не означает общий deadline40с: fsync/БД
могут занять дополнительное время. Точные значения/платформенные границы — IMPORT_API.

Ответы ошибок имеют фиксированные коды и максимум20 allowlist path/code issues без
значений/сырых сообщений. Диагностика multipart не пишет входные байты в логи.
stdout manifest дочернего валидатора — приватный pipe, stderr не публикуется.
React дополнительно ограничивает диагностические пути, текст экранируется.

package_storage пишет случайный файл0600 в приватном каталоге0700, fsync, атомарно
устанавливает SHA256.detective через hardlink без перезаписи и fsync каталога. Уже
существующий файл сверяется по размеру/checksum с O_NOFOLLOW. Метаданные фиксируются
только после долговечного пакета. CLI использует тот же atomic storage/hash lock.

Checksum PostgreSQL advisory lock согласует одинаковые байты между комнатами/CLI.
После rollback cleanup вновь проверяет любые committed ссылки под той же блокировкой;
используемый пакет не удаляется. Неоднозначный COMMIT не повод удалять файл. Общей ACID
транзакции БД+FS нет: при crash/недоступной БД возможны приватные неиспользуемые bytes
или служебный остаток; доступного частичного дела/ссылки на недописанный файл нет.
Повтор проверяет/reuses digest, не повреждает сохранённые сценарии. Backup требует
и PostgreSQL, и CASE_STORAGE_PATH. Автоматическая публичная GC/retention — не этап6.

Повтор тех же байтов/исходного ID в комнате возвращает прежний case и
already_imported=true; другой файл под прежним ID получает CASE_ID_CONFLICT409.
Другая комната может импортировать те же байты независимо, без выдачи чужого каталога.
Файл физически может быть общим по checksum, права остаются комнатными.

### Защита, backup и retention

APP_ENV=production требует HTTPS/exact origins, Secure cookies, persistent absolute
case path, явные точные trusted proxy IP и включённые HTTP budgets. Секреты читаются
из bounded regular `_FILE` без symlink; direct+FILE одновременно запрещены. Alembic
использует тот же DATABASE_URL_FILE reader. __Host-/HttpOnly/SameSite=Lax/Path=/,
CSRF, WSS guard, приватные assets/import/WS limits сохранены.
HTTP token buckets ограничены4096ключами: общий2400/мин burst240, sessions30/мин burst10,
create10/мин burst5, join60/мин burst20, import12/час burst3. Исчерпание даёт429/Retry-After,
спуфинг XFF не создаёт новую идентичность бюджета. Обычный JSON≤32KiB имеет timeout10с.

infra/ops.py требует явные env/project. Init не перезаписывает секреты; private parent0700,
file-backed API secrets0444 доступны только внутри закрытого каталога, backup copies0600.
Start собирает, останавливает API/proxy выбранного проекта перед миграцией, готовит
БД/роль/cases и открывает трафик только после health. Maintenance-lock сериализует ops.

Backup останавливает API/proxy и сохраняет pg_dump, cases, Caddy TLS data/config,
pepper/DB secrets/publicenv, реальные schema head/image IDs и SHA256 manifest.
Ранее работавшие сервисы возвращаются в finally. Restore принимает только доверенный
backup с проверенными checksum/безопасными TAR и только совершенно пустой target project.
Сохраняет target origin/порты/сеть, возвращает прежние секреты, БД/архивы/сертификаты.
Destroy разрешён только явно помеченному detective-test-* с --test; проверяется ownership.
Backup содержит закрытые данные/секреты и требует шифрования перед offsite-переносом.
Встроенной отправки/шифрования нет; версия кода/образов хранится оператором отдельно.
Автоматического downgrade нет; c6e20a4f9137 с импортами намеренно не откатывается.

Retention — только предложение: lobby30д без активности, unfinished90д, FINISHED90д,
импорты до удаления всех ссылок комнаты/партий, expired sessions grace30д, orphan≥7д
после проверки ссылок и backup. Автоочистки нет. Для реализации нужны достоверные
last_activity/finished_at, правила touch и отдельный dry-run, а не created_at как суррогат.
Срок cookie30д не гарантирует возвращение в комнату, которая хранится90д.
