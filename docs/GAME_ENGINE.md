# Контракт игрового движка — этап 1

Пакет: `backend/detective/game_engine`. Не зависит от FastAPI, SQLAlchemy, PostgreSQL,
HTTP, WebSocket и браузера. Новых зависимостей нет; существующий валидатор используется
для сценария при создании/восстановлении.

## Состояние и вызовы

- `create_game(game_id, manifest, players, host_id)` создаёт LOBBY с выбранным валидным
  сценарием и фиксированным составом 2–8 игроков, в пределах meta.min/max_players.
  Комнаты/выбор сценария до создания этого состояния — сервис этапа 2 (API.md).
- `apply(state, actor_id, command, rng=None)` возвращает Transition с новым состоянием
  и событием StateChanged(revision, phase). Ошибка — GameError со стабильным code.
  Входное состояние никогда не изменяется. Отмена возвращает то же состояние без события.
- `actor_id` доверенный: сервис обязан разрешить его из аутентифицированной сессии.
  В командах нет actor_id/owner_id/host-флага. Сам движок не аутентифицирует браузер.
- `rng=Random(seed)` нужен для тестов; обычный запуск использует SystemRandom.
  Случайность потребляется только при StartGame. Восстановление не вызывает StartGame.
- GameState, вложенные объекты и коллекции неизменяемы (frozen dataclasses и tuple).
  Карты в зонах представлены ID. Содержимое сценария хранится единожды как проверенная
  неизменяемая JSON-строка внутри Scenario; manifest() возвращает отдельный словарь.
  Это сохраняет существующий контракт 1.0.0 без второй схемы сценария.
- hand_for(member_id) возвращает только ID во внутреннем серверном состоянии.
  GameState/Scenario/Hand/Transition не включают секреты в repr и не логируются движком.

## Команды и фазы

| Команда | Фаза и права | Результат |
| --- | --- | --- |
| StartGame | LOBBY, ведущий | Перемешать колоду и очередь, раздать по кругу: 3 при двух игроках, иначе 2; INTRO |
| BeginPlay | INTRO, ведущий | PLAYING, первый игрок из сохранённой очереди |
| PlayCard | PLAYING, владелец в свой ход | Одна публикация или закрытый сброс, до одного добора, следующий непустой игрок |
| ProposeFinish | DISCUSSION, любой участник | Сохранить предложение |
| ConfirmFinish | DISCUSSION, ведущий, есть предложение | ANSWERING |
| SelectAnswer | ANSWERING, любой участник | Выбрать/заменить один вариант в общем наборе |
| SubmitAnswers | ANSWERING, ведущий, заполнены все вопросы | REVIEW, выбор блокируется |
| ReviewAnswer | REVIEW, ведущий | Сохранить ручную отметку; после проверки всех вопросов автоматически RESULTS |
| FinishGame | RESULTS, ведущий | FINISHED; результат остаётся доступен |

PlayCard содержит PlayMode, ID карты, позицию для публикации и confirmed.
`confirmed=False` — отменённое/неподтверждённое действие, не меняет ревизию/ход/руку.
Призрак и модальные подтверждения появятся в UI; фиксировать сброс разрешено только
после обязательного подтверждения пользователем. Для публикации с отключённым диалогом
клиент отправляет confirmed=True после отпускания. Сервер не может доказать показ диалога.
Координаты должны быть конечными числами. Стартовая карта размещается в (0, 0).
Рисование, перемещения открытых карт и камера сюда не входят.

При исчерпании колоды руки доигрываются без добора, пустые руки пропускаются.
После последней карты автоматически DISCUSSION, активного игрока нет.
Повторное предложение отклоняется; повторный выбор варианта заменяет общий выбор.
Ручную отметку можно исправить, пока REVIEW не завершён. Последняя отметка фиксирует
итог и переводит в RESULTS; после этого пересчёт/редактирование запрещены.
Правильность берётся из ручных отметок, даже если они отличаются от ключа.

## Инварианты и восстановление

`check_invariants` проверяет зоны всех карт (ровно одна на карту), общую стартовую
карту, владельцев рук, порядок участников, непустую активную руку, условия фаз,
валидные ответы, отсутствие преждевременной проверки/результата и точность счёта.
Он вызывается при создании, до и после каждого изменения и при сохранении/восстановлении.

`dump_state` / `restore_state` — **только серверное сохранение**, содержащее все секреты.
Внутренний конверт имеет state_version=1 (это не format_version сценария).
Восстановление проверяет структуру, версию, сценарий и инварианты, не раздаёт карты
и не повторяет команды. Никогда не отправлять этот конверт клиенту.

Ревизия увеличивается на одно успешное подтверждённое изменение. У движка нет журнала
client_action_id: транзакционная дедупликация повторов и expected_revision относятся
к этапу 2. Повтор сыгранной карты отклоняется правилами, но это не замена идемпотентности.
Нет блокировок, БД, cookies, heartbeat и сетевого восстановления.

## Клиентские представления

`public_state` — общие данные комнаты; `private_state_for` добавляет только руку
указанного участника и, исключительно ведущему в REVIEW, ключ вопросов.
Выбор полей явный, полный сценарий никогда не копируется в клиентское состояние.

В REVIEW ключ содержит correct_option_id, explanation, evidence_card_ids, но не solution,
role, logic_notes или supports_questions. До REVIEW ключ закрыт всем. В RESULTS/FINISHED
публикуются разгадка, ключ, роли/объяснения карт, сброс и расчёт очков.
Декларации изображений выдаются только для видимых карт (включая собственную руку).
Ссылки shareable не публикуют фрагменты автоматически. Событие StateChanged содержит
только ревизию и фазу; сервис запрашивает персональные представления отдельно.

Представления не заменяют проверку членства в транспортном слое и авторизацию
загрузки самого изображения. public_state допустим только для участников комнаты;
API обязан выбирать private_state_for по собственной сессии, а не по ID из URL.

## Проверки

Все проверки запускаются командами корневого README; существующий CI уже охватывает
новый пакет и tests/test_game_engine.py. Генерируемые pytest-тесты проверяют свойства
на 140 партиях (7 размеров группы × 20 seed), всего 2240 ходов, без новой библиотеки.
Это ограниченная генерация последовательностей, без автоматического shrinking Hypothesis.

Слой REST/хранения этапа 2 использует этот контракт без изменения ядра.
Сетевые сессии и журнал повторов не входят во внутренний конверт game_engine.

Уточнение проекции этапа 4: в REVIEW ведущему также выдаются private.reviewed_answers
с уже сохранёнными ручными отметками (question_id, reviewed_correct), чтобы после F5
не вести параллельную клиентскую проверку. У остальных участников этого поля нет.
Правила, внутреннее состояние и команды не изменены.
