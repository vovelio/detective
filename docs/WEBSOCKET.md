# WebSocket protocol v1 — этап 3

WebSocket синхронизирует сведения о подтверждённых изменениях, presence и временные
курсоры. PostgreSQL — источник истины. Игровые команды выполняются только через REST
этапа 2 с CSRF, ревизиями и прежней идемпотентностью. На этапе 4 React-клиент реализован; интерактивная доска добавлена на этапе 5 (BOARD_API.md).

## Подключение

1. POST `/api/v1/sessions` выдаёт или восстанавливает анонимную cookie.
2. Клиент должен быть участником комнаты (POST join для первого входа).
3. Открыть `/ws/v1/rooms/{code}` с subprotocol `detective.v1`; в HTTPS использовать WSS.
4. Получить hello, загрузить актуальный персональный REST-snapshot по snapshot_url.
5. Отправить resume с ревизией **полученного snapshot**, обработать synced/sync_required.

Handshake проверяет cookie через существующий HMAC/session механизм, членство,
единственный точный Origin из ALLOWED_ORIGINS и Host с портом из тех же origins.
Неправильные/дублированные Host/Origin, любой query string, чужая/просроченная сессия,
отсутствие subprotocol отвергаются до accept. Секреты нельзя передавать через URL,
subprotocol или поля сообщений. Браузер автоматически отправляет HttpOnly cookie.
CSRF-токен в WS не нужен: игровые команды не принимаются, а Origin обязателен.

Перед accept отказ обычно выглядит как HTTP 403; неверный HTTP handshake (например,
два Host) может получить 400 от Uvicorn. Браузер часто сообщает только error/1006,
не раскрывая HTTP-код. Причину собственной сессии можно уточнить REST-запросом.

## Форматы

Все сообщения — текстовый JSON, `protocol_version: 1`. Неизвестные входящие поля,
actor_id, member_id, card_id/тексты в cursor, неподдерживаемые типы и версии запрещены.
Идентификатор отправителя курсора определяется только сервером из сессии.

### Сервер → клиент

```json
{"protocol_version":1,"type":"hello","member_id":"<свой member UUID>","revision":2,"phase":"PLAYING","snapshot_url":"/api/v1/rooms/<code>/snapshot","heartbeat_seconds":15}
```

hello **не содержит** руку, ключ, cookie или внутренний state. Snapshot получают
через REST, где работают те же персональные views и проверки ресурсов.

```json
{"protocol_version":1,"type":"state_changed","revision":3,"phase":"PLAYING"}
{"protocol_version":1,"type":"room_changed","revision":0,"snapshot_url":"/api/v1/rooms/<code>/snapshot"}
{"protocol_version":1,"type":"presence","sequence":4,"players":[{"member_id":"<UUID>","online":true}]}
{"protocol_version":1,"type":"cursor","member_id":"<UUID>","x":12.5,"y":-20}
{"protocol_version":1,"type":"ping"}
{"protocol_version":1,"type":"pong"}
{"protocol_version":1,"type":"synced","revision":3}
{"protocol_version":1,"type":"sync_required","revision":6,"reason":"missed_events"}
```

- state_changed — уведомление о новой подтверждённой игровой ревизии. Поля строго
  ограничены revision/phase; не пересылается даже весь game_events.public_json.
- room_changed — состав лобби/выбранное дело изменились, нужно перечитать snapshot.
  Это отдельный тип, потому что join/выбор сценария не увеличивают игровую revision.
- presence — весь текущий список member_id/online. sequence упорядочивает presence
  внутри жизни room-stream; после нового подключения счётчик клиента нужно сбросить.
  Участник online, пока остаётся хотя бы одно его активное соединение. Временный обрыв
  не удаляет членство/руку, не меняет ведущего, очередь или ревизию.
- cursor — эфемерное сообщение другим соединениям своей комнаты; хранение в БД,
  история, привязка к картам и рисование отсутствуют. При offline курсор нужно удалить.
- sync_required — получить свежий REST-snapshot. reason: missed_events, event_gap,
  client_ahead, event_gap_or_backlog, subscription_race. Причина — диагностика, не
  игровая команда. При реальном откате ревизии БД старый сокет закрывается с 1012.
- error с фиксированным code может предшествовать закрытию при ошибке протокола,
  но не гарантируется при перегрузке. Значения присланного JSON не отражаются.

Ключ в REVIEW и разгадка в RESULTS/FINISHED доступны по REST только в разрешённом
представлении. Их нет в WS-сообщениях даже ведущего. Изображения по-прежнему выдаются
через `/api/v1/rooms/{code}/assets/{asset_id}` с персональной проверкой видимости.

### Клиент → сервер

```json
{"protocol_version":1,"type":"resume","revision":3}
{"protocol_version":1,"type":"pong"}
{"protocol_version":1,"type":"ping"}
{"protocol_version":1,"type":"cursor","x":12.5,"y":-20}
```

resume подтверждает ревизию snapshot в браузере, не пересылает и не применяет игровой
ход. Целое revision: 0…2147483647. Даже future revision не принимается на веру:
сервер отвечает sync_required с авторитетной ревизией. cursor — только конечные
числа x/y в диапазоне ±1 000 000; никакой приватный текст не передаётся.

## Порядок, гонки и восстановление

На активную комнату — один poller с интервалом 250 мс. Он не читает games.state:
только фазу/ревизию, сохранённые события и публичный состав комнаты. REPEATABLE READ
даёт согласованную пару games.revision/game_events. Неподтверждённая транзакция,
rollback, повтор client_action_id и отмена без смены ревизии не порождают уведомление.
Задержка обычно до одного интервала плюс время DB/отправки; это не hard real-time SLA.

Непрерывные события читаются по revision и отправляются по очереди. Начальный watermark
сокета — ревизия handshake, поэтому уже учтённые события не дублируются ему. Если общий
poller прошёл дальше, новая подписка получает sync_required. Если во время REST-fetch
произошёл COMMIT, resume обнаружит более свежую games.revision. При backlog >128 или
пропуске сохранённого события отправляется sync_required вместо неполной последовательности.
resume сверяет games.revision и наличие GameEvent в PostgreSQL; механизм восстановления
не зависит только от памяти процесса. Исторические snapshot/руки не воспроизводятся.

Алгоритм для UI этапа 4:

1. На каждое новое соединение создать новое поколение локального транспорта. Получить
   hello и **всегда** запросить snapshot, даже если revision кажется прежней: лобби могло
   измениться при revision=0, а после восстановления БД серверная ревизия может быть ниже.
2. Хранить applied_revision отдельно от target_revision уведомлений. Не разыгрывать
   карты из событий. state_changed лишь инициирует загрузку актуального snapshot.
3. Разрешать один snapshot-fetch одновременно, объединять несколько уведомлений в один
   следующий запрос. Устаревшие события revision <= applied_revision игнорировать;
   room_changed требует refresh и при равной revision. Не позволять позднему HTTP-ответу
   старого поколения соединения заменить состояние нового.
4. После применения snapshot отправить resume с его revision. Если получен sync_required
   или за время fetch пришла большая target_revision — повторить fetch. synced означает,
   что на момент проверки snapshot соответствовал известной подтверждённой ревизии.
   Следующий COMMIT будет обнаружен poller независимо от момента этой проверки.
5. Немедленно отвечать pong на ping. Presence/курсор обновлять отдельно от игры.
6. При временном разрыве сохранить cookie/членство, показать «Переподключение…» и повторять
   подключение с backoff, например 0.5/1/2/4/8/10 с плюс jitter. После подключения начать
   с пункта 1. Не создавать новую комнату/игру и не вызывать start повторно.
7. Неизвестный результат REST-команды повторять с **тем же** client_action_id, payload и
   expected_revision. После квитанции перечитать snapshot. Идемпотентность — этап 2.

Персональный snapshot остаётся HTTP-ответом для конкретной cookie. Два сокета одного
участника не дают доступа к другой личности. Новый процесс начинает presence заново,
а игровые карты/членства/роль/фаза/ревизия остаются в PostgreSQL.

## Лимиты и очистка

| Ограничение | Значение | Причина |
| --- | --- | --- |
| Входящий текстовый JSON | 4 KiB | только короткие control/cursor, без игровых материалов |
| Исходящий кадр | 8 KiB | hello/presence для максимум 8 участников |
| Очередь writer | 64 сообщения и 256 KiB | ограничение памяти и задержки медленного клиента |
| Общий inbound rate | 20 сообщений за скользящую секунду | heartbeat/resume и ограниченный cursor |
| Cursor rate | до 10/с | лишние координаты отбрасываются, надёжная история не нужна |
| Соединения | 4 на участника, 32 на комнату, 256 на процесс | несколько вкладок с ограниченной памятью |
| Poll interval / event batch | 250 мс / 128 | один DB-reader на комнату, bounded catch-up |
| DB timeout / send timeout | 5 с / 5 с | зависшая БД/сеть не держит ресурс бесконечно |
| App heartbeat | ping каждые 15 с, timeout 45 с | обнаружение исчезнувшего/зависшего клиента |
| Uvicorn transport | inbound 4096, queue 8, compression off | ограничение буфера до ASGI-handler |

На сокет один writer; никакая рассылка не ждёт отправки всем клиентам по очереди.
При overflow/timeout соединение закрывается с 1013; после reconnect нужен snapshot.
В очередь не кладётся полный сценарий или чья-либо рука. Входящие/исходящие сообщения
и cookie не логируются; access log отключён локальным runner, debug WS запрещён.
Дополнительно Uvicorn использует transport ping 15 с / pong timeout 30 с.

Коды закрытия: 1000 обычное, 1001 shutdown/disconnect, 1003 binary не поддерживается,
1008 нарушение протокола/лимита сообщений, 1009 превышение размера, 1012 требуется
новый baseline после отката БД, 1013 перегрузка/медленный клиент/DB timeout,
4401 истечение сессии/потеря разрешённого членства, 4403 исчезла комната/партия,
4408 app-heartbeat timeout. При 4401 нужно проверить сессию по REST, а не автоматически
захватывать чужое место; потерянная cookie не восстанавливается гарантированно.

При закрытии отменяются и ожидаются receiver/writer/heartbeat и вспомогательные tasks;
освобождаются очередь и ссылки на сокет. После последнего соединения комнаты poller
отменяется, room-stream удаляется. При истечении сессии poller закрывает её сокеты,
не удаляя членства/карты. Shutdown отменяет poller до закрытия DB engine.

## Границы реализации

Один серверный процесс без Redis/межпроцессного presence. API и GameEvent обеспечивают
восстановление, но WS не обещает exactly-once доставку при обрыве. Повторы/пропуски
безопасно устраняются snapshot/revision, а игровые команды — прежней идемпотентностью.
Курсоры не составляют реализацию доски. React-адаптер с backoff и визуальным состоянием
соединения реализован на этапе 4 (FRONTEND.md); работоспособность протокола проверена реальными
WebSocket-клиентами и двумя изолированными Chrome-контекстами с перезагрузкой страницы.

Локальные команды и тесты: LOCAL_API.md. Официальные API, использованные при работе:
[Starlette WebSocket](https://www.starlette.io/websockets/),
[websockets asyncio client](https://websockets.readthedocs.io/en/15.0.1/reference/asyncio/client.html).


## Дополнение этапа 5 — временное движение публичных карт

`card_preview` — единственное новое эфемерное сообщение, оно не является игровой
командой. Точные поля/проверки — [BOARD_API.md](BOARD_API.md). Клиент передаёт только
card_id/x/y/rotation/version уже опубликованной карты; сервер проверяет сессию,
членство, фазу, публичность и версию по PostgreSQL. Другим сокетам отправляет allowlist
с серверным member_id. Ни приватные призраки, ни текст карты/ключи не принимаются.

До8 preview/сек отдельно от cursor10/сек в общем20/сек. React ограничивает cursor4/сек
и preview8/сек для запаса control-сообщениям. Preview не пишется в БД, истекает через2с,
сбрасывается при reconnect и заменяется подтверждённой более новой object version.
Итог drag/rotate — REST board_mutation с expected_version, receipt и GameEvent.

Для долговечных объектов по-прежнему используется state_changed и REST snapshot,
сохраняющие прежний порядок ревизий/resume и безопасность. board_changed не понадобился:
одна общая games.revision остаётся для игрового состояния и объектов доски.


## Production WSS этапа7

Caddy принимает HTTPS/WSS и сохраняет публичный Host/Origin. Uvicorn доверяет
forwarded scheme/client только точному Caddy peer, не произвольному X-Forwarded-For.
Secure-cookie guard по-прежнему требует wss, сессию/членство и detective.v1.
Один API-процесс и прежние limits/presence/recovery сохранены. Настройка и отдельный
локальный TLS-test — DEPLOYMENT.md и DOCKER_OPERATIONS.md. Backup сохраняет pepper,
БД, кейсы и Caddy TLS data, чтобы восстановление могло продолжить прежнюю сессию.
