# Persistence и REST API — этап 2

## Границы

Реализованы локальный backend, доска этапа 5 (BOARD_API.md) и HTTP-импорт этапа 6
(IMPORT_API.md). Docker/Caddy и публичное развёртывание пока не реализованы.
На этапе 3 добавлены WebSocket и presence: протокол описан ниже.
На этапе 4 добавлен React-клиент: FRONTEND.md и LOCAL_UI.md.
Встроенные сценарии добавляются CLI; ведущий импортирует собственное дело через лобби
до запуска. Импортированное дело доступно только участникам своей комнаты.
Демо — учебное дело, не релизный детектив.

## Данные

- anonymous_sessions: UUID, HMAC-SHA256 opaque token, время создания/истечения.
- rooms: UUID, случайный код приглашения, ведущий, выбранный сценарий.
- members: UUID участника, комната, сессия, нормализованный ник, seat.
- scenarios: проверенный manifest JSONB, версия, checksum, имя серверного ZIP-пакета,
  nullable scope_room_id (NULL — встроенное дело; UUID — приватный каталог комнаты).
- rooms.catalog_revision: безопасный счётчик изменения каталога для room_changed.
- games: одна партия на комнату, фаза, ревизия, серверный state JSONB.
- game_actions: уникальные (game_id, session_id, client_action_id), hash запроса,
  ревизия и безопасная квитанция результата.
- game_events: уникальные game_id/revision, только безопасная фаза/ревизия для аудита.

Ведущий связан составным отложенным FK с участником именно своей комнаты.
Членство, ник и seat имеют ограничения уникальности; seat находится в диапазоне 0–7.
После старта новые игроки не добавляются; существующий участник может вернуться.
Ники: NFC, крайние пробелы удаляются, длина 2–20, управляющие/форматные символы
запрещены, сравнение дубликатов через casefold.

game_cards/team_answers пока не нормализованы в отдельные таблицы: серверный конверт
ядра хранит все зоны, очередь и ответы одним JSONB. Это уменьшает риск частичной
записи и сохраняет чистое ядро. Фаза/ревизия в колонках меняются с JSONB в одной
транзакции. Полный снимок включает неизменяемую копию сценария для самостоятельного
восстановления партии; scenarios хранит каталог и ресурсный пакет.

Alembic — явный шаг до запуска сервера, никаких create_all или миграций на HTTP-запросе.
Текущий head — c6e20a4f9137 после 9ab31d5e42c0 и 15d25b13ab98; alembic check сверяет ORM.
Downgrade импорта отказывается работать при наличии комнатных дел, чтобы не раскрыть
их как встроенные и не удалить существующие партии.
DATABASE_SCHEMA по умолчанию public; тесты используют изолированные test_<uuid> схемы.

## Сессия и безопасность

POST /sessions создаёт случайный token из 32 байтов, cookie HttpOnly, Secure,
SameSite=Lax, Path=/, без Domain; в Secure-режиме имя __Host-detective_session.
Срок — 30 дней от создания, без автоматического продления. В БД только HMAC токена.
TOKEN_HASH_PEPPER должен сохраняться при перезапуске, минимум 32 байта.

Повтор POST /sessions с действующей cookie возвращает CSRF proof и список своих комнат,
member_id/место и роль сохраняются. Это точка восстановления для будущего UI после F5.
Неверная/истёкшая cookie получает 401, существующая идентичность не заменяется молча.
Без cookie создаётся новая сессия, доступа к старому членству у неё нет.

Обычные POST требуют точный Origin из ALLOWED_ORIGINS, Content-Type application/json и
отсутствие Sec-Fetch-Site: cross-site. Кроме bootstrap /sessions, POST также требует
X-CSRF-Token из ответа /sessions. Он привязан HMAC к конкретной сессии и проверяется
constant-time сравнением. Bootstrap защищён Origin/JSON и не выполняет игровых действий.
Клиент не может задавать session_id/actor_id/host_id: лишние поля отклоняются.
Авторизация выполняется по cookie на каждом запросе и проверяет членство в комнате.

Не включён CORS с credentials. Host проверяется по ALLOWED_ORIGINS. Отключать Secure
можно только для origins localhost/127.0.0.1/::1 при локальной разработке.
Cookie и CSRF proof — не способ восстановить идентичность после удаления cookie.

Обычный POST-body ограничен 32 KiB, в том числе при chunked-передаче. Единственное
исключение — точный multipart-маршрут /rooms/{code}/cases/import: Origin/Host/сессия/
CSRF/права сохраняются, отдельные лимиты тела/времени описаны в IMPORT_API.md. Ошибки не отражают body,
cookie, ORM и SQL-параметры. SQLAlchemy echo=False и hide_parameters=True.
Ответы, включая ресурсы, получают Cache-Control: no-store, private, nosniff и
Cross-Origin-Resource-Policy: same-origin для запрета встраивания на другом origin.
Рекомендуемый локальный запуск отключает access log; приложение не пишет секреты в логи.
Публичные rate limits, HTTPS-прокси, backup/restore и эксплуатационные меры — этап 7.

## Транзакции, ревизии и повторы

Каждый запрос имеет собственную AsyncSession/транзакцию. Изменение комнаты блокирует
rooms; игровая команда дополнительно блокирует games через SELECT FOR UPDATE.
Порядок блокировок единый — комната, затем партия. Это сериализует старт, вход и команды
в одной комнате, но не блокирует другие комнаты.

После проверки членства ищется прежний action ID, **до проверки expected_revision**.
При совпадении fingerprint возвращается прежняя квитанция, без повторного применения.
Fingerprint включает тип, payload и expected_revision; повтор должен содержать тот же
запрос. Иное содержимое под тем же ID — 409 ACTION_ID_REUSED.

Новый action ID со старой ревизией — 409 REVISION_CONFLICT с текущей revision.
Движок получает actor_id из серверного членства. Новое состояние, фаза/ревизия,
квитанция и безопасные события записываются в одной транзакции. Ответ отправляется
после COMMIT; исключение откатывает всё. Уникальное ограничение action ID дублирует
защиту на уровне БД. Непринятые команды не резервируют ID и не меняют ревизию.
Отменённый PlayCard сохраняет квитанцию, но не меняет состояние/ревизию и не создаёт событие.

Квитанция: client_action_id, revision, phase. Она не содержит snapshot. После неё клиент
запрашивает актуальный персональный /snapshot, особенно после ретрая или конфликта.
Повтор старого запроса не возвращает прежнюю руку или содержимое сброшенной карты.
Start имеет ту же защиту; повтор не перемешивает и не раздаёт карты снова.
Новые action ID на повторный старт после старта отклоняются.
Создание комнаты/выбор дела/вход не используют client_action_id; восстановить список
уже созданных комнат можно через /sessions, повторный join возвращает прежнее членство.

## Ресурсы и секреты

Публичной директории пакетов нет. CLI и HTTP-импорт проверяют ZIP существующим валидатором,
пишет файл по SHA256-имени и сохраняет manifest/checksum в БД. Замена уже установленного
case ID другим содержимым отклоняется. Файлы каталога должны оставаться на постоянном
диске вместе с БД; их нельзя считать временным кэшем.

Asset endpoint вычисляет private_state_for и допускает только assets видимых карт.
Закрытая колода, чужая рука и сброс не дают разрешения, даже если ID/путь известен.
Пакет читается только с серверного пути, ограничивается размер, сверяется checksum;
PNG/JPEG/WebP проверены при установке. После сброса доступ исчезает и у бывшего владельца.
В REVIEW ключ только ведущему, но это не даёт доступа к изображениям закрытого сброса.
RESULTS/FINISHED разрешают ресурсы всех карт. manifest/state/ZIP клиентам не выдаются.
Уже увиденную карту браузер может помнить; no-store запрещает дальнейшее HTTP-кэширование,
но сервер не может удалить информацию из человеческой памяти.

## Проверка

Инструкции: LOCAL_API.md. Интеграционные тесты работают только при явно заданном
TEST_DATABASE_URL с именем базы detective_test*. Каждому тесту создаётся отдельная схема,
миграции выполняются настоящим Alembic; удаляется только эта схема. Если URL не задан,
тесты явно пропускаются. CI задаёт URL и использует PostgreSQL 18.1.

Конкурентные запросы и rollback проверяются на PostgreSQL. Restart-тест запускает
на loopback реальный Uvicorn, делает действия, аварийно завершает процесс, запускает
новый и проверяет прежние cookies/руки/роль/ревизию/квитанцию.

При реализации сверены официальные разделы
[SQLAlchemy asyncio](https://docs.sqlalchemy.org/en/20/orm/extensions/asyncio.html) и
[Alembic asyncio](https://alembic.sqlalchemy.org/en/latest/cookbook.html#using-asyncio-with-alembic).


## WebSocket — этап 3, protocol_version=1

Подробный протокол и алгоритм клиента: [WEBSOCKET.md](WEBSOCKET.md).
Endpoint: `/ws/v1/rooms/{code}`, subprotocol `detective.v1`. Cookie устанавливается
обычным POST /sessions; браузер отправляет её сам. Query string запрещён — не передавайте
токен или CSRF proof в URL. Handshake проверяет Origin, точный Host (включая порт),
сессию и членство. В Secure-режиме нужен WSS. Сокет не принимает игровые команды.

После handshake сервер отправляет hello с revision и snapshot_url, затем presence.
Клиент получает безопасный REST-snapshot по своей cookie и отправляет resume с его
ревизией. Сервер отвечает synced или sync_required; во втором случае snapshot нужно
повторить. Так обнаруживается COMMIT между загрузкой snapshot и подпиской/подтверждением.
На каждом переподключении snapshot обязателен, даже если revision не изменилась:
ревизия относится к игре, а состав лобби и presence меняются отдельно.

Подключённые комнаты читают подтверждённый PostgreSQL outbox каждые 250 мс. Одна
REPEATABLE READ транзакция согласует ревизию игры и game_events. Уведомления содержат
только revision/phase, а не сохранённый public_json целиком и не внутренний state.
Доставка не зависит от вызова callback в REST-процессе: коммит того же сервисного слоя
из другой сессии PostgreSQL также обнаруживается. Rollback, отмена и идемпотентный
повтор не порождают второе уведомление об изменении игры.

Непрерывные ревизии отправляются по порядку. При разрыве журнала или backlog >128
событий сервер отправляет sync_required с актуальной ревизией; клиент читает последнее
состояние, а не пытается восстановить карты из исторических событий. resume проверяет
сохранённую games.revision и наличие событий в PostgreSQL; память процесса не является
единственным механизмом восстановления. После рестарта presence строится заново,
членство, ведущий и игровое состояние остаются в БД.

Presence отражает активные соединения: один участник online, пока открыта хотя бы одна
его вкладка. Онлайн-статус не меняет game revision, руку, роль и очередь. room_changed
сигнализирует о составе лобби/выбранном деле и требует REST-snapshot. cursor — только
конечные координаты и серверный member_id, без card_id/текста/ресурсов, без сохранения.

Лимиты: входящий JSON 4 KiB; исходящий кадр 8 KiB; очередь 64 сообщения и 256 KiB;
20 входящих сообщений/с и до 10 cursor/с на соединение; 4 сокета на участника,
32 на комнату, 256 на процесс. Отправка и DB-запрос ограничены 5 с. Heartbeat каждые
15 с, отсутствие входящих валидных сообщений 45 с завершает соединение. Медленные
клиенты закрываются с 1013 и должны переподключиться с новым snapshot.

Локальный runner `python -m detective.api` дополнительно ограничивает WS на уровне
Uvicorn (4 KiB, очередь 8, compression off) и отключает access log. При прямом запуске
Uvicorn нужно передать те же параметры; общий REST-лимит не распространяется на WS.
Никакие cookie/кадры/личные карты не логируются; debug-логирование WS включать нельзя.

## Дополнение этапа 5 — доска

`board_objects` хранит transform публичных карт и аннотации с версиями/tombstones.
Snapshot дополнен allowlist `board.objects`. Согласованность с games.revision
обеспечена блокировкой game при чтении проекции. Мутации выполняются прежней транзакцией
с receipt/outbox и той же анонимной сессией. GameState меняет только revision;
игровые правила/формат сценария не менялись.

Исключение из строгой общей ревизии: только board_mutation принимает прошлую
expected_revision, проверяя точную версию изменяемого объекта. Независимые объекты
сохраняются оба; конкурентное изменение одной версии даёт BOARD_VERSION_CONFLICT.
Клиент явно сообщает, что правка не сохранена, и перечитывает snapshot.
Подробные DTO, лимиты и эфемерный WS card_preview — [BOARD_API.md](BOARD_API.md).

## Production-защита этапа7

В APP_ENV=production обязательны Secure/HTTPS/exact origins, отдельный persistent
CASE_STORAGE_PATH и точное доверие Caddy IP. Секреты доступны из ограниченных `_FILE`.
Обычный HTTP Host сверяется целиком с портом; /api/* требует HTTPS-схему от доверенного
proxy. Ограничение HTTP-запросов возвращает RATE_LIMITED429/Retry-After; обычный JSON
сохраняет32KiB и дополнительно имеет timeout10с. Импорт/WS сохраняют прежние лимиты.
Параметры/бюджеты/защита ошибок — PRODUCTION_SECURITY.md; HTTPS-инфраструктура — DEPLOYMENT.md.
