# Импорт пользовательских сценариев — этап 6

## Контракт HTTP

- `GET /api/v1/cases` — только встроенные дела, прежний контракт.
- `GET /api/v1/rooms/{code}/cases` — члену комнаты: встроенные + импортированные
  именно в эту комнату. Ответ только `[{id,meta}]`, без манифеста/рук/ключей/разгадки.
- `POST /api/v1/rooms/{code}/cases/import` — ведущему в LOBBY, до создания GameState.
  Cookie + разрешённый Origin/Host + `X-CSRF-Token`; multipart/form-data с **одной**
  файловой частью `file`, без других частей/полей. Имя/MIME клиента не используются
  как доказательство типа или путь на диске. Источник истины — байты ZIP/валидатор.

Успех200:

```json
{"case":{"id":"upload-<opaque hash>","meta":{"title":"..."}},"already_imported":false}
```

`meta` — полный обычный публичный объект метаданных сценария по формату1.0.0.
Выбор не меняется автоматически: ведущий явно выбирает дело существующим `/cases/select`.
Начало использует прежний `/start`, сервер копирует проверенный manifest в замороженную
партию. Импорт/выбор после старта отклоняются, уже запущенная партия не меняется.

Ошибка валидации422:

```json
{"error":{"code":"CASE_VALIDATION_FAILED","message":"CASE_VALIDATION_FAILED","issues":[{"path":"/play_cards/0/id","code":"DUPLICATE"}]}}
```

Не более20 проблем, пути до128 символов: только известные имена полей схемы/числовые
индексы; прочее заменяется `/`. Нет исходных значений/авторских текстов/содержимого ZIP.
Ошибки не логируются с input/body; диагностические строки стороннего multipart-парсера
подавлены. Пайп валидатора с manifest не является публичным API/логом.

Коды: CASE_ID_CONFLICT409, IMPORT_LOBBY_ONLY409, CASE_LIMIT409, INVALID_MULTIPART422,
IMPORT_TOO_LARGE413, IMPORT_TIMEOUT504, IMPORT_BUSY503, CASE_STORAGE_UNAVAILABLE503,
IMPORT_PROCESSING_FAILED422, IMPORT_PROCESSING_LIMIT422; прежние auth/Origin/CSRF-коды.
Строки ошибок фиксированные; UI локализует их без интерпретации HTML.

## Изоляция и повторы

В `scenarios` добавлен nullable `scope_room_id`; NULL означает встроенное операторское
дело. Импорт получает opaque ID `upload-` + SHA256(room UUID + ':' + исходный manifest.id).
Исходный manifest.id/format_version не переписываются. Одинаковый исходный ID в разных
комнатах допустим, доступ между ними отсутствует. Select и start независимо проверяют scope.

Повтор одинаковых байтов в той же комнате возвращает прежний case ID и
`already_imported:true`, не создаёт копию и не меняет каталог повторно. Тот же исходный
ID с другими байтами — CASE_ID_CONFLICT: существующее дело неизменно. Для исправленной
версии автор должен назначить новый исходный ID. Идемпотентность здесь содержимая,
дополнительный client_action_id для upload не нужен. После потерянного ответа безопасно
перезагрузить каталог/повторить тот же файл; автоматического повторного выбора/start нет.

`rooms.catalog_revision` увеличивается только на новый успешный импорт. Существующий
WS room_changed обнаруживает изменение по этой безопасной метке, клиенты перечитывают
room-scoped каталог. Новый WS payload с манифестом не вводится.

## Лимиты и изоляция валидатора

Существующий validator1.0.0 не ослаблен: ZIP≤20MiB, распаковка≤80MiB, ≤100 файлов,
16млн пикселей/изображение, regular files, только manifest и объявленные PNG/JPEG/WebP;
без извлечения архива, ZipSlip/симлинков/дубликатов/исполняемых файлов/вложенных ZIP.
Обработка изображений проверяет реальное декодирование, MIME/расширение — дополнение.

HTTP импорт ограничивает:

- весь multipart body≤20MiB+64KiB, сам файл≤20MiB;
- boundary1–200 printable ASCII, ≤8 заголовков части, ≤8KiB строка заголовка;
- одна часть `file`, поток читается не более30с; chunked тоже проверяется по байтам;
- два одновременных импорта на процесс, третий получает IMPORT_BUSY без чтения файла;
- ≤16 импортированных дел в комнате; повтор прежнего файла допускается и при лимите;
- отдельный короткоживущий Python-процесс валидации: wall10с, CPU5с,
  RLIMIT_AS512MiB где поддерживается ОС; результат manifest≤8MiB;
- по таймауту/отмене дочерний процесс принудительно завершается и ожидается,
  а не продолжает работу в неостанавливаемом фоне.

Глобальный JSON/32KiB предел остальных POST не меняется. Исключение multipart относится
только к точному маршруту импорта. Авторизация ведущего проверяется **до** чтения тела,
затем повторно вместе с фазой/сессией после валидации под room→game locks. Если ведущий
успел запустить игру, загрузка не сохраняет сценарий и не меняет партию.

Это не обещание жёсткого wall40с всего endpoint: ОС-записи/fsync и ожидание PostgreSQL
могут занять дополнительное время. Публичная защита от глобального злоупотребления,
retention/backup/эксплуатационные лимиты относятся к этапу7.

Parser — зафиксированный `python-multipart==0.0.34`, проверенный по
[официальному PyPI](https://pypi.org/project/python-multipart/). Другие зависимости не обновлялись.

## Согласованность файла и PostgreSQL

Приватный файл хранится как SHA256.detective, режим0600, каталог0700. Сначала запись
в случайный служебный файл, flush/fsync; затем atomic hardlink без overwrite в digest
путь и fsync каталога. Уже существующий файл проверяется по размеру/checksum с
O_NOFOLLOW. Ни временное имя, ни путь не берутся из клиента. Незавершённая запись не
видна под окончательным именем. CLI использует тот же механизм и advisory checksum lock.

Импорт удерживает PostgreSQL advisory transaction lock, производный от checksum,
для одинаковых байтов в разных комнатах/CLI. Метаданные записываются только после
публикации долговечного файла. Scope/catalog revision и metadata фиксируются вместе.
При ошибке/rollback после попытки записи cleanup снова берёт hash lock, проверяет
отсутствие **любых** committed references в scenarios и только тогда удаляет orphan.
Файл, которым уже пользуется другая комната или встроенный сценарий, не удаляется.

Общей атомарной транзакции PostgreSQL+файловая система нет. При kill процесса между
публикацией файла и COMMIT либо недоступной БД/неоднозначном результате COMMIT возможен
лишь приватный unreferenced digest-файл/служебный остаток; видимого частичного дела
и committed ссылки на недописанный файл не возникает. Не удаляем файл при
неподтверждённом отсутствии ссылок. Повтор загрузки проверяет/reuses digest, восстанавливая
обычный путь без повреждения старого сценария. Пакеты и БД требуется сохранять вместе.
