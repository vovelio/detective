# React-интерфейс и интерактивная доска — этапы 4–5

Интерфейс React/TypeScript/Vite использует существующие REST и WebSocket. Новых игровых
механик нет. Состояние расследования приходит только с сервера, команды не применяются
оптимистично. Локальные drag/rotate previews отделены от подтверждённого snapshot.
Встроенная голосовая связь и аккаунты не добавлены.

## Структура

- src/contracts.ts — только клиентские представления и типы существующих команд.
- src/api.ts — same-origin fetch, cookie, CSRF в памяти, локализованные безопасные ошибки.
- src/realtime.ts — detective.v1, hello/snapshot/resume, объединение обновлений,
  защита от старых HTTP-ответов, presence/pong, watchdog и bounded reconnect.
- src/session.ts — анонимная сессия, URL комнаты, последний серверный snapshot,
  состояние загрузки и сохранённое намерение команды.
- src/App.tsx — подписка React через useSyncExternalStore, навигация и общие сообщения.
- src/screens.tsx — главная, лобби, вступление/игра, обсуждение, ответы, проверка, итоги.
- src/components/{Card,Dialog,Players}.tsx — карточки, подтверждения и состав участников.
- src/board/BoardGame.tsx — интерактивная доска, HUD, временные жесты, приватный ghost.
- src/board/geometry.ts — камера, экранные/мировые координаты, зум относительно указателя.
- src/styles.css — единая нейтральная система, закреплённый HUD на desktop, мобильная адаптация.
- vite.config.ts — только локальный сервер/proxy. /api и /ws направляются в backend,
  Host/Origin не подменяются. Vite не получает секреты через переменные VITE_*.

Дополнительные клиентские библиотеки состояния, роутер и UI-kit не требуются.
Node test runner используется для автоматических проверок адаптеров, без Vitest/jsdom.
Браузерные E2E используют существующий CDP/Chrome-инструментарий проекта.

## Экраны

Главная: имя 2–20 Unicode-символов после trim/NFC, создание/вход по коду или ссылке,
список своих комнат. Создание комнаты не повторяется автоматически при потерянном
ответе: пользователь может обновить список комнат из существующей сессии.

Лобби: ведущий, участники и настоящие WS-статусы, приглашение с копированием, выбор дела,
объяснение недоступного старта. На этапе6 «Добавить свою игру» открывает форму
CaseImport ведущему в LOBBY: состояния загрузки/ошибки/успеха/неизвестного результата,
безопасная диагностика, обновление комнатного каталога, без автоматического выбора.

Игра: полноэкранная доска под компактными HUD. Слева сверху «Игроки» со стрелкой
сворачивания и фиксированной колонкой точки хода, сверху инструменты, справа шестерёнка
и сброс размером около одной карты, справа снизу открытая своему владельцу рука.
Описание/вопросы/настройки/предложение финала — в шестерёнке. Вопросы выдаются в прежних
разрешённых фазах, до них пункт объясняет доступность. Импорт реализован в лобби на этапе6.

Публикация и сброс — перетаскиванием. Призрак личной карты только локальный.
После отпускания публикация подтверждается по умолчанию; её можно отключить в меню.
Сброс всегда подтверждается; отмена не отправляет команду. Координаты публикации —
точные мировые координаты указателя в момент отпускания с учётом pan/zoom.
Сервер одной командой размещает карту, добирает и передаёт ход.

Камера индивидуальна: пан за пустое поле, «Рука» панорамирует с любой точки доски.
Колесо/совместимые wheel-жесты трекпада масштабируют относительно указателя; есть +/−
и «К центру». Камера не посылается серверу и после F5 возвращается к исходной области.
Публичные карты фиксированного размера можно двигать/вращать специальной ручкой;
просмотр кнопкой «Читать» открывает полный текст/фото. Resize/group отсутствуют.

По явному уточнению владельца этапа 5 стрелки свободные, создаются протягиванием
между произвольными точками (прежний запрет FINAL отменён). Карандаш создаёт штрихи,
ластик удаляет целые штрихи/стрелки/заметки, но не игровые карты. Простой текст заметок
экранируется React. Все участники равноправно редактируют доску INTRO/PLAYING/DISCUSSION,
в финальных фазах она доступна для просмотра. Данные/команды — BOARD_API.md.

Технические значения, не пиксельный эталон дизайна: карты 240×320 мировых единиц,
зум 0.2–2.5, единый цвет карандаша, максимум 256 точек штриха/1000 символов заметки.
Временное движение публичной карты идёт через WS card_preview до 8/сек; курсор — до
4/сек (сервер допускает 10), оставляя запас для resume/heartbeat в общем лимите20/сек.
Preview исчезает через2с, cursor через15с, оба очищаются при reconnect/offline.
Canonical version новее preview имеет приоритет. Частые previews не пишутся в БД.

Долговечная мутация идёт через прежний controller/идемпотентный REST. На drag-start
сохраняется версия объекта, на release — команда с этой версией. Изменение другого
объекта/общей revision не сбрасывает текущий drag или заметку. Stale target даёт
явное сообщение, актуальный snapshot; автоматического overwrite нет. Во время обычного
snapshot-refresh (syncing) можно продолжить действие, при реальном обрыве — нельзя.

После разыгрывания карт любой предлагает завершение, ведущий переводит к вопросам.
В ANSWERING варианты управляются серверным snapshot и видны всей команде. Ведущий
подтверждает окончательную отправку в модальном окне. В REVIEW выбор заблокирован;
ключ и ручные отметки видит только ведущий. RESULTS/FINISHED показывают объяснение,
хронологию, ответы, разбор значимости карт, штрафы и серверный счёт. Окончательно
завершает ведущий, результат остаётся доступным.

## Восстановление и неоднозначный результат запроса

Cookie HttpOnly не читается JavaScript. После F5 bootstrap восстанавливает членство,
а URL /rooms/{code} — текущую комнату. В WS нет токенов в URL или игровых команд.
На hello всегда читается новый snapshot; после него resume подтверждает именно его
ревизию. state_changed/sync_required/room_changed вызывают актуальный fetch, несколько
уведомлений объединяются. Старое поколение соединения не может заменить новое состояние.

Backoff — 0.5/1/2/4/8 секунд с jitter, максимум 10 секунд; новый snapshot обязателен
после reconnect. Ответ pong на ping отправляется сразу. Клиентский watchdog: 15 секунд
до первого сообщения, 45 секунд без сообщений. Online/offline браузера также запускают
восстановление. Во время обрыва показывается «Переподключение…», изменяющие кнопки
недоступны. Уже доступную свою руку можно читать; ход/роль из-за обрыва не меняются.

Перед первым POST игровой команды или мутации доски формируется UUID и в sessionStorage сохраняется
намерение (kind, code, memberId, client_action_id, expected_revision, payload).
Ключ отдельный для комнаты: detective.pendingAction.v1:{code}. Там нет CSRF/cookie,
полного snapshot, текстов карт или ключа автора. Намерение заметки содержит введённый
пользователем публичный текст аннотации; оно удаляется после подтверждённого результата. Токены в localStorage не сохраняются;
localStorage содержит только настройку подтверждения публикации.

При потере ответа/5xx намерение не удаляется, новые команды блокируются. Пользователь
может повторить сохранённый запрос с **тем же** UUID/ревизией/payload, в том числе после
F5. Квитанция дедуплицируется сервером; затем читается актуальный snapshot. Сам факт
новой ревизии не считается доказательством получения квитанции этого запроса.
При окончательном отказе 409/422 намерение снимается, состояние перечитывается; новый
запрос с новым ID возможен только после нового явного действия пользователя.
При ошибке CSRF сохранённый запрос можно повторить после bootstrap с актуальным proof.
Намерение другого member_id не отправляется от новой сессии.

Если cookie истекла/потеряна, старые карты удаляются из React/DOM и показано объяснение.
Автоматического захвата прежнего места нет. Истёкшую HttpOnly cookie нельзя удалить
через JS: для нового входа предлагается удалить данные сайта в настройках браузера.
Это не восстановит прежнюю идентичность. Новый reset/auth endpoint не добавлялся.

## Минимальное расширение snapshot

Обнаруженный пробел этапов 1–3: REVIEW-snapshot не включал уже сохранённые ручные
отметки ведущего. UI не мог восстановить ход проверки после F5, не ведя параллельное
клиентское состояние. Добавлено только в private_state_for ведущего в REVIEW:

```json
{"private":{"reviewed_answers":[{"question_id":"q1","reviewed_correct":true},{"question_id":"q2","reviewed_correct":null}]}}
```

Гостям поле недоступно; публичная проекция/WS/правила подсчёта/фиксация ответов не менялись.
Данные берутся из существующего состояния, новые команды/миграции не понадобились.

## Проверки и ограничения

Node-тесты адаптеров; TypeScript strict; Prettier; production build; pytest/реальный
PostgreSQL; UI E2E с двумя изолированными Chrome-контекстами и отдельным профилем.
Полный UI-сценарий проходит от создания до FINISHED, включая картинки, подтверждения,
F5, offline/reconnect и потерю ответа после COMMIT с повтором старого ID.
Проверяются также приватные отметки REVIEW после F5, cookie deletion/expiration,
отсутствие чужих карт и мобильная ширина. Скриншот делается только на главной до карт.

Прототип не является приёмкой MVP: нет VPS/HTTPS
инфраструктуры и реальной партии друзей с релизным оригинальным делом.
Команды запуска — LOCAL_UI.md. Пользовательские действия проверены в настоящем Chrome,
но это автоматизированная локальная партия с учебным делом, не живая приёмка.

Зафиксирован Vite 6.4.6: версия включает исправление, указанное в официальном
[advisory Vite](https://github.com/vitejs/vite/security/advisories/GHSA-p4f5-76q4-ffq7).
Никакой публичной экспозиции dev-server нет; актуальный npm audit сообщил 0 уязвимостей.


## Импорт этапа 6

ApiClient передаёт file в FormData с cookie/CSRF, не задавая Content-Type вручную;
браузер формирует boundary. Отдельный таймаут50с, JSON-команды остаются прежними.
Комнатный каталог читается при WS-refresh/F5, вручную и после успеха. Generationguard
и AbortController исключают запись старого ответа в другую комнату. При неизвестном
результате предлагается обновить список и при необходимости повторить тот же файл.
Архив/его содержимое не пишутся в localStorage/sessionStorage. Ошибки локализуются по
фиксированным кодам; пути/число issues дополнительно ограничены клиентом. Подготовка
и сценарии пользователя — IMPORT_GUIDE.md, серверный контракт — IMPORT_API.md.


На этапе7 refresh после старта использует один персональный snapshot: состав/ведущий/
фаза берутся из него, каталог после старта неизменяем. В лобби room/catalog по-прежнему
обновляются при room_changed/импорте. Это уменьшает нагрузку совместного стола и общий
NAT budget без изменения серверных прав/модели игры. Ошибки429/timeout/неверного HTTPS
имеют понятные фиксированные сообщения.
