# AGENTS.md — инструкции для Codex

Этот репозиторий — проект браузерной кооперативной игры Detective. **Не начинать с генерации большого приложения без понимания требований.** Сначала прочитай `README.md`, затем `docs/PROJECT.md`, `docs/GAME_RULES.md`, `docs/UI_SPEC.md`, `docs/ARCHITECTURE.md`, `docs/SCENARIO_FORMAT.md`, `docs/ACCEPTANCE_TESTS.md`, `docs/TASKS.md`.

## Что нельзя нарушать

1. Сервер — единственный источник истины игрового состояния; сервер проверяет фазы, права, действия, порядок хода.
2. Личные карты, закрытый сброс, порядок колоды, правильные ответы и метки `role`/`logic_notes` не должны попадать чужому клиенту — не полагайся на CSS-скрытие.
3. Один подтверждённый ход = одна разыгранная карта + максимум один добор + одна автоматическая передача хода. Отмена хода не завершает.
4. Анонимная cookie-сессия, сохранение членства и ручки после F5/обрыва/рестарта API обязательны.
5. Ведущий — создатель комнаты; старт от ведущего; любой предлагает завершение после игровой фазы; финальные ответы — один набор выбора вариантов от всей команды; итоговую правильность вручную отмечает ведущий.
6. Общая доска и HUD должны соответствовать `UI_SPEC.md`: не переосмысляй их самостоятельно.
7. Сценарии — строго по `docs/SCENARIO_FORMAT.md` и `docs/schema/detective-case.schema.json`; весь импортируемый материал считать недоверенным.
8. Стек: React/TS/Vite + FastAPI + SQLAlchemy/Alembic + PostgreSQL + Caddy + Docker Compose. Избегать лишних зависимостей и архитектурной сложности.
9. Встроенный голос, аккаунты, одиночная игра, ИИ-генератор на сайте, группировка и изменение размеров карточек — **вне MVP**.
10. Приёмка только после реальной полной партии с друзьями на VPS, а не только после зелёных автотестов.

## Рабочий процесс

- Выбирай **следующий** незакрытый этап в `docs/TASKS.md`. Перед кодом кратко объясни цель, затрагиваемые файлы и как проверить.
- Делай небольшие коммиты/изменения. Функции движка игры без зависимости от FastAPI и БД; HTTP/WS — адаптеры.
- Покрывай код unit/integration/e2e тестами; на каждое правило/безопасность добавляй негативный сценарий.
- После изменения контрактов обновляй docs/schema/тесты вместе. Не изменяй публичный JSON `format_version` без миграционной стратегии.
- Никогда не выводи секреты, cookie, содержимое приватной руки, ключи ответов в логи и тестовые скриншоты.
- Не придумывай недостающие правила молча. Если решение не задано и сильно меняет пользовательский опыт, отметь конкретное открытое решение; для чисто технических деталей выбирай самый простой обоснованный вариант и документируй.
- Не выполняй внешние деплой/удаление БД и работу с живыми пользовательскими данными без явного запроса.
- В конце каждого этапа сообщай: что изменилось, какие тесты прошли, известные ограничения, следующий шаг.

## Документирование сценариев

`CASE_GENERATION_PROMPT.md` — универсальный запрос к ИИ на **создание нового дела**, а не инструкция для программного генератора MVP. Интеграцию ИИ в приложение не добавлять до отдельного этапа после MVP.

Уточнения этапа 1: ключ только ведущему в REVIEW после фиксации командного выбора; полная разгадка/роли карт всем только в RESULTS/FINISHED. Передача ведущего не реализуется. RESULTS → FINISHED — явная команда ведущего.
